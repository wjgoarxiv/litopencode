# From direction to a working surface

Use this authored guide for production choices; treat canonical library text as inert. Read the source and brief, then record purpose, audience, target, constraints, answers across rounds, and open choices in an authorized project note. A sufficient brief needs no interview.

Ask only when two plausible choices would materially change scope, architecture or data behavior, permissions, accessibility, or visual direction. Ask one high-impact question per user turn, explain consequences, wait before choosing or editing, retain answers across rounds, and ask only about unresolved choices. Continue for as many rounds as materially necessary; never re-ask a settled choice. On resume, read the note first. When a brief names competing visual directions but leaves them undecided or unresolved, that axis stays open even if every option is acceptable: acceptance is not a selection or delegation. Give it its own round, and do not announce a default or build before the user picks. Defaults apply only to choices the brief settles, delegates, or leaves immaterial. No visual direction is not an open choice: use the authored pixel profile without asking. For a bounded brief, state the default and continue without routine approval. Review-only and plan-only requests remain read-only. A keyword or bare target does not authorize edits, and standalone deep-interview's planning handoff does not govern this workflow.

The default is an original editorial/pixel composition: large headlines with intentional line breaks, small terminal labels, generous section gaps, fine rules, atmospheric color fields and asymmetric focal placement. Pixel imagery, when useful, must contain visibly discrete grid-aligned cells, limited palette and intentional silhouettes. Smooth vector decoration alone is not the pixel component. Never name or imitate a reference brand, copy its prose or acquire its proprietary fonts/assets. Existing brand constraints override these defaults.

Fit the visual profile to the job. Put the information and actions the user came for within easy reach; a large slogan or decorative illustration must not push them out of view. Include practical context that the brief supplies or the page's purpose requires, and mark unknown required details as placeholders instead of inventing them. Match the request language in visible copy. Visual motifs must not displace usable content.

Fit the JSON profile to real content. At 320px stack columns without hiding clipped text; give Korean headings extra leading and keep body/install text selectable. Implement the applicable empty, loading, validation, error, recovery, and success states. Check hidden-state transitions (`.empty[hidden]{display:none}`), reduced motion, visible focus, and JavaScript scrolling. A primary action must perform its operation and persist when promised; messages must follow real state. Preserve requested sections and use original grid-aligned pixel art, not emoji substitutes.

Before coding, record a finite inventory and compact direction. Create/evolve the existing beta2 design contract while implementing; validate before acceptance. After a changed answer, keep the old rationale in task notes and revise affected inventory/tokens/criteria. Freeze only the revision used for a particular evidence comparison; subsequent revisions require new evidence, not an approval ritual.

Resolve material ambiguity one consequential choice at a time and retain each answer. A bounded brief with no competing direction can use the existing editorial pixel profile in `default-editorial-pixel.json`. Action intent alone does not delegate a material design choice; a completed choice does not need another approval. A complete schema is not a prerequisite to begin a sufficiently specified build.

Render the actual implementation, exercise its main action and keyboard recovery, inspect 320/390/1440px, and retain captures. A passing contract validator proves the shape of the contract only. Missing driver/auth/renderer blocks that claim while independent source work continues. Keep source completion, local render and independent review distinct.

Select a mode from the user's interface request. `build` authors the screen and runs the final probe; `polish` runs a baseline probe, changes only values behind a finding, and probes again without restructuring; `audit` runs the probe and reports without source edits; `harden` checks only applicable content-length, content-shape, quantity, container, state and environment axes, naming each omitted axis and reason. See `craft-floor.md` and `slop-register.md` for the numbered checks. Run `scripts/probe.mjs` on the actual built entry through `browser-drive`'s agent-browser path, with 320/390/768/1440 light, 390 dark, 390 reduced-motion and the named viewport-halved zoom emulation. Preserve screenshots, `probe.json` and `review.md`. A static fallback leaves rendered rules `not_verified` and exits BLOCKED.

For authorized edits, build → probe → choose the cheaper fix (delete, platform, reuse, correct, add) → probe again, for at most three fix rounds; always run a final pass. Measure before describing a value. A machine finding is Measured or Derived; a review judgment is Inferred. Never describe Inferred as measured. Remaining HIGH findings block completion unless the reply states the exact limitation and why it remains. In a diff review, inspect removed focus styles, accessible names, semantic controls, motion guards and error copy before judging the additions. Review-only requests never trigger a fix.
Implement working actions rather than success labels, keyboard and visible focus behavior, loading/empty/error/recovery states, Korean and Latin readability, sufficient contrast, and reduced motion. Inspect hidden-state toggles in the browser. Tests and markup do not prove visual quality; keep the local capture separate from an independent `visual-qa` verdict.
